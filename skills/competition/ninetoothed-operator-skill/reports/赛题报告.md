## 摘要

本作品是一个可复用的 NineToothed 算子开发 `.skill`，目标是让评委指定的统一 AI
智能体在面对陌生算子任务时，能以**低方差、正确性优先**的固定工作流一次性完成开发、
测试、调试、性能分析与集成。设计的核心判断是：由于每个隐藏任务只运行一次、且因
skill 引导错误导致的失败不重跑，skill 应当优化"不失败"而非"表现惊艳"。作品的四个
自测算子全部在真实硬件（RTX 5060, CUDA 13.0, torch 2.13.0, triton 3.7.1）上通过，
并包含一个真实的性能回退诊断闭环（约 20000× 提升）。

## 1. .skill 目标、设计原则与包结构

### 1.1 目标
构建一个指导 AI 智能体为 NineToothed 生态编写、验证、优化、调试和集成算子的
`.skill`，覆盖从"算子需求"到"正确且有性能意识的实现"的完整闭环。不修改编译器核心。

### 1.2 设计原则（对齐评分机制）
评测有三个决定性特征，直接推导出三条设计原则：

| 赛制特征 | 设计原则 | 主要得分项 |
|---|---|---|
| 65 分压在"陌生 AI + 8 陌生算子 + 各跑一次" | 仓库检索优先于内置知识 | 任务完成度、仓库风格 |
| 每题一次、引导错误失败不重跑 | 正确性优先的固定工作流 | 完成度、测试验证 |
| 单题 6/10 在正确+测试 | NineToothed 专属故障恢复表（单次运行内自救） | 完成度、测试、减少引导失败 |

核心哲学：**不赌智能体聪明，赌流程低方差。** 锁死 65 分的正确性，再用可执行脚本与
A/B 证据吃工程可用性与自测材料的 20 分。

## 2. 核心工作流

SKILL.md 将任意算子任务约束为一条八步流水线，AI 不得跳步：

0. **归类**：判成四车道之一——L1 逐元素/广播、L2 归约/分块、L3 布局敏感、
   L4 性能/诊断/集成。
1. **先读仓库**：按索引表读同类现成算子（如 softmax→`tests/test_softmax.py`），照抄结构。
2. **抽语义**：input/output/shape/dtype/broadcast/边界。
3. **判布局**（不可跳）：是否保证 contiguous？布局敏感必须设计一个非连续输入测试。
4. **最小实现**：arrange-and-apply；application 参数是 block 而非整张量；多输入
   最外层 shape 必须用 expand 对齐；不动 `src/ninetoothed/`。
5. **验证闭环**：写 PyTorch reference → 生成 pytest → 运行；无 GPU 如实 skip。
6. **性能**（仅在相关时）：do_bench 出五要素，或查 generated source / AOT build。
7. **失败自救**：查故障表，最小修复，重跑，记录闭环。
8. **合规门**：只改 competition 目录、无硬编码答案、无删/绕测试、无密钥、不伪造结果。

三种辅助手段分别落位：**流程约束**（写在 SKILL.md，管顺序）、**知识注入**
（references/，补 DSL 知识）、**工具提供**（scripts/，把验证从手写变调用）。

## 3. 自测算子任务、运行过程与 correctness 结果

四个自测覆盖四类隐藏任务，全部在真实硬件运行通过。

| ID | 车道 | 算子 | correctness |
|---|---|---|---|
| T1 | 逐元素/广播 | elementwise multiply | `1 passed` |
| T2 | 归约/分块 | row softmax | `1 passed` |
| T3 | 布局敏感 | 2-D multiply（连续 + 非连续） | `2 passed` |
| T4 | 性能/诊断 | multiply benchmark + 回退诊断 | 见 §5 |

一次性复现命令与结果：
```bash
pytest skills/competition/ninetoothed-operator-skill/examples -v -p no:cacheprovider
# => 4 passed in 15.76s
```

- **T1** 选择 elementwise multiply（而非仓库样例 add），用同样安全的 `*` 原语，
  证明 skill 不是"照抄样例"而是可泛化。
- **T2** 严格复用仓库 softmax 范式：行 tile `(1, BLOCK_SIZE)`、`constexpr` 行宽、
  `Tensor(other=-inf)` 边界填充、`ntl.max/exp/sum` 数值稳定实现。
- **T3** 是本作品最有说服力的一条：**非连续（转置）输入也通过**，证明 NineToothed
  正确处理 stride，也证明 skill 强制的"测非连续输入"这一步真实可执行——正是多数
  智能体会跳过、从而丢掉两道布局敏感隐藏任务的地方。

环境：WSL2 Ubuntu / RTX 5060 (8GB) / CUDA 13.0 / torch 2.13.0+cu130 /
triton 3.7.1 / ninetoothed 0.26.0（editable）。

## 4. benchmark 设计、输入规模、结果与结论

benchmark 通过 `scripts/bench.py`（封装 `triton.testing.do_bench`，warm-up 后计时）
对 elementwise multiply 与原生 `torch *` 对比，报告五要素。

| 规模 | torch 基线 | NineToothed | 对比 |
|---|---|---|---|
| 2^20 (1,048,576) | 0.0489 ms | 0.0459 ms | 1.07× 更快 |
| 2^24 (16,777,216) | 0.6026 ms | 0.6125 ms | 1.02× 慢（噪声内） |

**结论**：逐元素乘是显存带宽瓶颈算子，两者都跑满带宽，落在彼此噪声范围内属于正确
结果——NineToothed 在此类算子上与 torch 持平即为预期。16M 处 1.02× 属运行间抖动，
非真实回退。

## 5. 失败诊断案例与修复闭环

作品包含一个**真实、可复现**的性能回退诊断（对应故障表第 12 条）：

- **症状**：首次 benchmark 显示 NineToothed 比 torch 慢 **22,068×**（982.6 ms vs 0.0445 ms）。
- **根因**：算子包装函数在**每次调用时重新定义并编译 `@ninetoothed.jit` kernel**，
  于是每次计时都在付编译与 auto-tune 开销——测的是编译时间而非计算时间。1M 元素的
  乘法不可能耗时约 1 秒，该量级本身就是"每次重编译"的特征。
- **最小修复**：kernel 只在模块加载时构建一次并复用（`_MULTIPLY_KERNEL`），只对
  kernel 调用计时。脚本内保留 `multiply_naive`（错误）与 `multiply_fixed`（正确）
  两条路径以演示对比。
- **重跑结果**：1M 规模 982.6 ms → **0.0459 ms**，约 20000× 提升，回落至与 torch 持平。

**沉淀进 skill 的经验**：NineToothed kernel 若显得异常慢，先怀疑"每次调用重编译/
auto-tune"，编译一次复用、只对调用计时，再下性能结论。

另有一个次要但同样真实的集成诊断：examples 接入仓库时报
`ModuleNotFoundError: No module named 'tests'`，根因是测试位于仓库根之下、根不在
`sys.path`；最小修复为新增 `conftest.py` 注入仓库根，未改任何测试或源码，重跑
`4 passed`。两个案例都体现"读第一个真实错误→定位根因→最小修复→重跑验证"的闭环。

## 6. 与不使用 .skill 的 AI 智能体基线对比

| 维度 | 无 skill 的通用智能体 | 装载本 skill 后 |
|---|---|---|
| 上手 NineToothed | 易把 DSL 当普通 PyTorch/裸 Triton 写，不知 arrange-and-apply | 第一步强制读同类现成算子，照 pattern 改 |
| 布局敏感 | 默认输入 contiguous，转置/切片输入静默出错 | Step 3 强制判布局 + 强制非连续测试（T3 实证通过） |
| 测试验证 | 常常写完不测，或无 PyTorch reference | 脚本生成 pytest + 一键 CI，验证近乎自动 |
| 性能 | 只说"优化性能"，或误报回退 | do_bench 五要素；诊断出"重编译"伪回退并修复 |
| 失败恢复 | 反复乱改（thrash） | 查故障表，最小修复，单次运行内自救 |
| 合规 | 可能删测试/绕测试凑通过 | 合规门显式拦截，任一违规即判无效 |

最直接的证据是 T3 与 §5：布局敏感的非连续用例、以及 20000× 的性能回退，都是通用
智能体最易翻车、而本 skill 的固定流程能稳定通过或诊断修复的场景。

## 8. 局限性与后续可维护计划

### 局限性
- 自测在单一 GPU（RTX 5060, sm_120）与 float32 为主验证；fp16/bf16、多 GPU、
  更大规模及 AOT `.so` 分发未逐一实测。
- T2 采用与仓库同构的 softmax 以确保正确性；更复杂归约（layernorm、attention）
  的模板已在 references 指明路径但未各自附独立自测。
- benchmark 聚焦带宽瓶颈的逐元素算子；计算密集型（matmul）的性能对比未展开。

### 后续维护
- 扩充 references 的算子模板与故障表条目（随仓库演进更新）。
- 为 L4 增补 generated source 检查与 AOT auto-tune 的可执行示例。
- 增加 fp16/bf16 与非连续归约的自测覆盖，持续对齐 CONTRIBUTING.md 的 CI 变化。
